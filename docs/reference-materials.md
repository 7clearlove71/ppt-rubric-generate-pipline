# PDF/PPTX 参考材料能力（2026-10-23）

当前协议实现 `2026-10-23.contract-v2.5.2`，Python 包版本 `0.2.1`，rubric validator 12、judge validator 12。命令仍为 `batch` / `contract-v2.5`，通用配置仍使用 `configs/contract-v25-*.json` 文件名，但其中 `contract_version` 已更新。旧配置、rubric及评分检查点不能混入新运行，不迁移或改写历史结果。

本页描述默认图文流程；2.5.2新增 `role_supports_images`，生成/审核/judge可独立只读文字，纯文本judge只评内容（原满分80）。纯文本遇无文本材料页明确失败，不丢页；具体行为、评分及示例以[按阶段配置能力](model-capabilities.md)为准。

## 输入与读取

任务的原始制作要求放在 `prompt.txt`，所有候选共用的材料放在 `attachments/`，候选各自放在独立目录的 `result.pptx`。即使来源PPTX本身叫 `attachments/result.pptx`，它也只作为材料。目录约定、相对名称和manifest结构见 [input-format.md](input-format.md)。材料不需要人工评测字段。

PDF每页渲染为PNG，并保留PDF文本层全文；扫描、图表、空文本页不会被丢弃，也不会合成OCR文字。PPTX按实际幻灯片顺序使用现有LibreOffice转换器生成PDF，再读取其页面图片和PDF文字；不将PPTX XML抽取文字当作视觉事实。隐藏页、加密PDF、空文件或不支持格式明确失败。PPTX备注、嵌入文件、音视频和动画过程不纳入来源范围，必要事实须放在可见页面。

每个材料页保留源文件SHA-256、相对名称、页码、渲染身份及图片SHA-256。页级来源目录在无文本时也生成引用ID，引用ID绑定文件、图片和实际文本。图片标签为 `material/attachment_N_page_P`，候选图片标签为独立文档ID，避免把材料当作待评分作品。

## 各阶段输入

| 阶段 | 实际输入 |
| --- | --- |
| 需求提取、审核后的重新提取 | 原始prompt、全部材料文字和全部材料页图片；不读取候选 |
| 逐条生成rubric | 当前requirement、任务摘要/来源政策、原始prompt、其source_ids所引用的材料页文字和图片 |
| full来源审核 | 原始prompt、全部材料文字和图片、完整rubric的id/content/dimension/score及既有评分约定 |
| 内容judge | 原始prompt、全部材料文字和图片、当前候选整稿图片及PDF辅助文字、一条rubric |
| 视觉judge | 原始prompt、全部材料文字和图片、当前候选一页及容量允许的局部图、全部5条独立视觉rubric |

不完全省略rubric编写阶段的原始材料：需求提取可能遗漏单位、限定条件或图示语义，保留引用页可供模型直接核对。也不在每条编写时重复全材料，避免无关页面干扰和重复传输。涉及附件的需求应在提取时引用对应材料页；引用选择是模型语义判断，程序能验证ID及文件绑定，不能证明选页正确或语义完整。

附件的每一句事实或每一处版式不自动变成制作义务。prompt应说明材料是事实来源、背景、结构参考还是视觉模板；提取提示词明确区分必需目标、背景与示例，保留时间、单位、对象和事实/计划状态。对于引用扫描页的rubric，文本层缺少某个计数约束不能证明该约束没有来源，因此原有纯文本计数检查转交图片语义审核；无图片依据的条目继续执行原检查。light仍跳过来源审核，不能据此声称这些语义判断已验证。

## 容量与缓存

默认 `max_source_pages=40`（所有PDF/PPTX总页数）、`source_dpi=120`。`max_case_text_chars=100000` 包含prompt和全部来源文字。`max_images_per_request=60` 为材料和候选合计：内容为 A＋P，视觉为 A＋1＋可用局部图，A是全部材料页数，P是当前候选页数。先保留全部材料和候选原页，再使用剩余容量生成候选局部图；不因加入材料丢弃必需原页。

需求提取/审核超限在该题生成调用前失败；judge在该题任何评分调用前检查所有候选的合计图片容量。batch各题独立推进，生成完成后才准备候选，因此某题后续评分容量失败前可能已发生生成调用。未实现大材料检索、分块摘要、自动抽页或OCR；超限明确失败，不静默截断。客户端页数/图片上限也不保证供应商的实际token容量。

batch材料缓存位于 `<run>/cache/materials/`；分阶段命令按 `--cache`，直接Python调用可指定 `source_cache_root`（默认 `.cache`）。缓存冻结一份PDF和全部图片，缓存记录自身也带指纹。同内容不同输入路径可共用缓存；原始输入仍按manifest校验。生成与评分需使用一致的材料渲染配置和缓存位置。来源、缓存PDF或图片变化、缺失时拒绝复用；不能删除材料缓存来保持原检查点续跑，仅删除API响应缓存不影响已持久成功结果的复用。

`plan`无模型API调用，但带附件时会执行本地材料转换/渲染并校验容量，PPTX仍需要可用的LibreOffice。plan输出各题材料页数、各阶段输入政策及图片容量公式。材料准备不增加模型逻辑调用：light仍 N＋1，full仍按实际轮次累计 Σ(N_r＋2)，judge仍 C＋P（无视觉时C）；附件会增加请求体和模型输入量，未声称耗时或费用保持不变。

## 验证范围

使用合成图表PDF、无文字扫描页、PPTX结构及转换替身，验证页面/引用、图文请求组装、light/full、引用页编写、全材料judge、文件和图片篡改拒绝、加密/隐藏页/容量失败及恢复。batch测试走实际Client的本地HTTP替身，核对请求中的base64图片、审核及评分携带材料，并删除API缓存后续跑；修改材料图后确认在新请求前拒绝复用。全套测试的真实HTTP传输被拦截。

附件增强首轮760项离线测试通过；当前能力分阶段的测试范围见[模型能力](model-capabilities.md)。无付费API调用、真实附件评测、人工一致率或模型阅读质量结论；PPTX新分支的自动化测试采用转换替身，未声称完成带真实Office转换的整批评测。历史任务及关闭授权保持，不恢复暂停的09。
