## 问题与责任

之前能计算人工一致率，是因为旧链路能完成生成与评分；2/6（33.3%）说明质量尚未达标。今天的 `2026-10-12.2` 实验同时引入新证据协议、GLM生成配置，以及更严格的归属和跨候选检查；后来换回K3时又没有恢复旧基线的一次来源细化与困难修订思考角色。模型、运行策略和协议同时变化，破坏了可比性。这是本次配置迁移和实现的回归，不能归咎于人工标签不可用。

证据提取器选错算式后，程序曾直接改写缺陷归属；一致性复核也曾把等价解释、单边unknown与调用失败放大成双边unknown。生成端让模型重复抄写精确边界与覆盖映射，导致本可确定性完成的字段成为阻断。原有93项测试全过但真实流程失败，说明仅有理想化假客户端测试不够。

## 防止再次发生

1. **固定基线后一次改变一个实验因素。** 记录生成器、审核器、judge、协议版本、修订策略、配置和源码哈希；模型或生成策略变化要单独列明，不能当作同一pipeline的纯提示词改进。
2. **确定性字段由程序生成，语义判断由模型核验。** 不用LLM抄写覆盖图、计算confirm集合或复制排除文字；也不把字符串正确当作语义正确。
3. **观察不是事实，计算执行正确不代表公式适用。** 原始错误提取必须可追查，不能向下游伪装成程序确认的缺陷。
4. **不确定性按候选、条目和阶段定位。** 区分作品确实不满足、资料不足、模型输出不合规、辅助复核不可用；报告完整覆盖率和复核覆盖率后再看一致率。
5. **把真实失败变成回归，再做小规模模型验证。** 测试通过不能替代看图与实际模型运行。先验证生成审核、算术、视觉、复核这些关键环节，之后才申请有范围、有上限的新批次。
6. **质量失败如实保留。** 不靠改人工标签、放宽所有约束、替换历史成绩或无限修订制造通过。每轮请求跨命令累计，关闭后的剩余额度不滚存。

## 现行运行方式

先用K3配置做生成或复审的离线plan；只有新版本approved产物才能进入正式评分：

```bash
python3 -m ppt_rubric plan --operation generate --cases 06 \
  --config configs/evidence-v1-k3.json --out artifacts/next-run/generation-plan.json
python3 -m ppt_rubric plan --operation judge --cases 06 \
  --config configs/evidence-v1-judge.json \
  --rubrics artifacts/evidence-fix-20261012/recheck06 \
  --out artifacts/next-run/judge-plan.json
```

plan只读本地数据，不构成调用授权。judge基础配置仍保留12次小规模上限；完整评分可能超过此值，执行前按plan明确范围和跨命令预算。百炼批量生产仍需新的明确授权。
